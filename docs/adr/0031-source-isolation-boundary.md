# 0031 — Source isolation boundary: every external database read in a worker without the lake

**Status:** Accepted (2026-11-07). The direction was approved by the Owner in #259 (2026-10-31); this record carries the implementation of #372, which the Owner merges.

This record makes **ADR-0025** precise (§4).

## Context
- **A database source can carry SQL of its own.** A DuckDB file holds views, macros and virtual generated columns; a SQLite file holds views. DuckDB runs that SQL in the session that reads it.
- **The attack is demonstrated on DuckDB 2.0.0** (#259):
  - an attacker builds a view `SELECT * FROM lake.main.sueldos` against a fake `lake` on their own machine;
  - read as a source in the lake's session, the view returned the victim's rows.

  `READ_ONLY` protects the source, not the lake, and the attack only reads.
- **The interim refusal was safe but too narrow.** Until now, a DuckDB source with views, macros or generated columns, and a SQLite source with views, were refused; legitimate views could not be read.
- **No DuckDB setting is a boundary between catalogs.** `search_path`, `READ_ONLY`, `enable_external_access`, a random lake alias (discoverable through `duckdb_tables()`) and `CONNECT` were all evaluated and rejected as the boundary (#259).

## Decision

### 1. The boundary
- **No database source is attached to the lake's connection.** This covers DuckDB files, SQLite files and PostgreSQL.
- **Each read starts a worker process of its own.**
  - It is spawned, never forked from the lake's process, with isolated Python and an environment that carries no secret.
  - It opens one DuckDB instance with only that source attached, read-only.
  - The request reaches it on standard input; the PostgreSQL password goes there too, never on the command line or in the environment.
- **Inside the worker, the source's views and macros work as the source defines them,** with no lake, no lake catalog and no lake secret to reach.
- **What crosses into the lake is only the statement's result,** one Arrow IPC record-batch stream. Its schema carries the statement's DuckDB types.
- **Parquet and CSV keep their direct path:** their views are generated by the store, never brought by the source.

### 2. The worker's configuration
The worker is configured, then locked, before any SQL of the source runs. The order is fixed and tested:

1. **Limits:** its share of the lake's limits (half the memory and half the threads; the lake keeps the rest, and one worker runs at a time), a private folder the parent owns and removes in every outcome. There is no OS address-space limit: DuckDB's allocator reserves virtual memory well beyond its own limit, and `RLIMIT_AS` made workers fail on CI runners (measured). DuckDB's memory limit, the split and the time limit bound a worker.
2. **Session:** `TimeZone` UTC and `arrow_lossless_conversion` on.
3. **Extensions:** only the source's own (`sqlite` or `postgres`), with autoload and autoinstall off.
4. **Attach:** the source read-only. PostgreSQL also gets a read-only session and a temporary secret.
5. **Sandbox:** `allowed_paths` limited to the source file, `enable_external_access` off, then `lock_configuration` on.

The statement guard, the table-function refusals and the inexact-column refusals run in the worker as they ran in the lake.

### 3. What a model may do
- **One connection only.** A model that reads a database source reads only that connection: any of its tables and views, but no other connection and no lake table.
- **The worker runs the whole SELECT,** with `$since` bound there for incremental models, and the parent lands the result in the model's lake table inside the run's write–audit–publish transaction.
- **Refusals at validation:**
  - a mixed model is refused with `SOURCE_MODEL_MIXED`;
  - a view model on a database source is refused with `SOURCE_MODEL_VIEW`, because it would be inlined into the models reading it.
- **Reconciliation against a database source** lands the source's grouped side from the worker, compares it in the lake, then drops it.
- **Consequence for authors.** A model reading an external database lands its data in a lake table first, and later models join on lake tables. Two external databases are never joined in one query.

### 4. ADR-0025 made precise
- **Forbidden:** DuckDB → Python objects (tuples, dicts, DataFrames) → DuckDB.
- **Allowed:** DuckDB → an Arrow record-batch stream, in-process or Arrow IPC → DuckDB.
- **The stream is read once, batch by batch, never held whole.**
- **Types are checked at both ends.** The worker sends the statement's own types. The lake compares them with the stream's types, and again with the landed table's types. Any difference refuses the run with `UNSUPPORTED_SOURCE_TYPE`, and nothing is kept.
- **The one declared conversion is `ENUM` to `VARCHAR`,** because DuckLake stores no `ENUM`.
- **Lossless export is required.** It was measured on DuckDB 2.0.0: with the default `arrow_lossless_conversion = false`, the `UHUGEINT` maximum arrives as `-1`, `HUGEINT` becomes `DECIMAL(38,0)`, `UUID` becomes `VARCHAR` and `BIT` becomes `BLOB`.
- **The landing writes no type or column text from the source into the lake's SQL:** it is `CREATE TABLE … AS SELECT * FROM` the stream. Only binding builds empty stand-in tables in a scratch lake from the worker's column names and types, quoted as DuckDB renders them, as it did before this record.

### 5. Failures
- **One failure fails one run, never the lake.** This covers a worker that dies, hangs, exceeds its limits or sends a malformed stream.
- **Time limit and cancellation:** the worker is killed at the run's time limit (`STORE_TIMEOUT`) or on cancellation (`STORE_CANCELLED`).
- **Any other early end is `STORE_SOURCE_FAILED`,** a new code with a redacted message.
- **Nothing is published, and no process or folder is left behind.**

### 6. Gate 4: the worker process is adopted
- **What it contains:** a crash, a hang or a runaway memory use triggered by a hostile or corrupt file, and a source's view that would otherwise run in the lake's process.
- **What it does not promise:** protection from arbitrary native code run through a DuckDB or SQLite parser bug by a process of the same OS user. As in #363, nothing is promised against processes of the same user.
- **Mitigation and limits:** DuckDB stays pinned at its latest stable release (ADR-0022). OS-level sandboxing (seccomp, Landlock, AppContainer) is not built.
- **Cost:** about one process start per read, and Arrow IPC serialization. The benchmark (`benchmarks/source-stream.md`) records it; the boundary never depends on that result.

## Alternatives considered
- **The rejected boundaries** listed in #259, with the evidence there: the random alias, `search_path`, `READ_ONLY`, `enable_external_access`, `CONNECT`, and the shared connection that SQLMesh and dbt-duckdb use.
- **A second DuckDB instance in the lake's process.** It isolates catalogs, but it contains neither a crash nor a memory exhaustion caused by a hostile file. It was rejected in favor of the worker process.
- **Rejecting all databases with views,** the interim state: safe, but legitimate views could not be read.

## Consequences
- DuckDB files with views, macros or generated columns, and SQLite files with views, are now read.
- Models that joined a database source with other data must land the source first.
- A database source is reached only when a model reads it: an unreachable source fails a run that reads it, and no other.
