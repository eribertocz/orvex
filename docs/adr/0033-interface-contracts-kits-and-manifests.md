# 0033 — Interface contracts, conformance kits and module manifests (amends 0004 rules 2–4)

**Status:** Proposed (2026-11-14, #486)

## Context
ADR-0004 makes modules talk only through contracts, but its contracts are data contracts: they say what crosses a boundary, never which operations a module offers. On 2026-11-14 no module imported another module's internals, yet `server`, the conformance runners, `tools/` and the repository tests used 65 internal paths of the modules (#486 §1), the boundaries check exempted `server` as the composition root, and no module had ever been installed or tested outside the repository. Nothing proved that another implementation of a module could replace it.

## Decision
1. **Interface contracts** (amends rule 2). Besides the language-neutral data contracts of `contracts/`, each module's operations are declared as an interface contract in `orvex.contracts`: a `typing.Protocol` whose public methods are the operations, and an `InterfaceContract` (`orvex.contracts.interface`) that names the contract, gives it a `MAJOR.MINOR` version, groups the operations into capabilities and lists the error codes each may raise through the contract's error type. Only values cross: the annotated inputs and outputs are plain values, enums, generated contract models and frozen dataclasses of them (`orvex.contracts.serializable`); no live object, connection or callable. `UNSUPPORTED_OPERATION` can never be declared: a capability is provided in full or not at all. The interface contract of module `<m>` lives in `orvex.contracts.<m>.interface`; its kit in `orvex.contracts.<m>.kit` (`orvex.contracts.registry`).
2. **Conformance kits.** Every interface contract ships a kit (`orvex.contracts.kit`): cases with a stable id, the operation they exercise and their expectation in words, a recorded case count and no skip list. A kit leaves no operation without a case. It runs on a fresh implementation per case, once in process and once through the serializing binding (`orvex.contracts.kit_run`, `binding`, `codec`), and passes only when every case passes both ways with the same results; a skip is a failure. An implementation that passes its contract's whole kit may replace the module.
3. **Consumers know contracts, not modules** (amends rule 3). `server` stays the only composition root, but only `server/assembly.py` names implementations, and only through each module's public `api` package. Every other consumer (`server`, the conformance runners, `tools/`, the repository tests) imports only `orvex.contracts`. `tools/checks/consumers.py` enforces it, in report mode until #486 step 7 makes it blocking and removes the `server` exemption.
4. **Module manifests** (amends rule 4). Each module ships `module.toml` (`orvex.contracts.manifest`): the interface contracts it provides (version, capabilities, the `api` attribute that implements each) and requires (version, capabilities), and the distributions its code and its tests import. Before the server starts, `assembly.py` refuses (exit status 3, `ASSEMBLY_REFUSED`) any combination in which a required contract has no implementation or more than one, a version that does not provide the required one, a missing capability, or an implementation lacking an operation of what it claims. Each module still owns its state alone (rule 4 unchanged); the manifest makes what it offers and needs explicit.
5. **Compatibility of behavior.** The record of every interface contract and its kit (`packages/contracts/interface-record.json`, `tools/contracts/interface_record.py`) is compared with the record at the last product release (`tools/contracts/interface_compat.py`): within a major version operations, signatures, capabilities, error codes and kit cases with their expectations may only be added. A break needs a new major version (rule 6 of ADR-0004 applies to it).
6. **Standalone modules.** `tools/ci/standalone.py` builds a module's sdist and, from it, its wheel, installs it in a clean environment outside the repository with only `orvex-contracts` beside it, checks that its imports equal its declared dependencies and that its tests import no repository helper, and runs its own tests there, where a skipped test fails.

## Alternatives considered
- **Interface contracts as language-neutral documents with generated protocols:** symmetrical with the data contracts, but it adds a generator and a second description of each signature to keep in step; the record of rule 5 already gives a language-neutral view of each interface for comparison.
- **A second, complete implementation of every module** (#486 revision 3): proves substitution but duplicates about 41,000 lines; the kits, the assembly check and one real substitution (the semantic result cache, #486 step 5) prove it at a fraction of the cost.
- **Process isolation now:** belongs to the workers of #156; rule 1's value-only crossing and the serializing binding make the contracts ready for it.

## Consequences
Every module gains a contract, a kit, a manifest and an `api` package, one module per step of #486, and its consumers move onto them; module error classes used across modules move into `orvex.contracts`. CI gains the interface record and compatibility check and the standalone job. The documents that say `server` knows the modules (`architecture/overview.md`, `AGENTS.md` §5, `engineering.md` §2 and §8, `modules/contracts.md`) are corrected when this ADR is accepted.
