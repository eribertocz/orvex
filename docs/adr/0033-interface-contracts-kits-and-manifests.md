# 0033 — Interface contracts, conformance kits and module manifests (amends 0004 rules 2–4)

**Status:** Proposed (2026-11-15, #486 revision 7)

## Context
ADR-0004 makes modules talk only through contracts, but its contracts are data contracts: they say what crosses a boundary, never which operations a module offers. On 2026-11-14 no module imported another module's internals, yet `server`, the conformance runners, `tools/` and the repository tests used 65 internal paths of the modules (#486 §1), the boundaries check exempted `server` as the composition root, and no module had ever been installed or tested outside the repository. Nothing proved that another implementation of a module could replace it.

## Decision
1. **Interface contracts** (amends rule 2). Besides the language-neutral data contracts of `contracts/`, each module's operations are declared as an interface contract in `orvex.contracts`: a `typing.Protocol` whose public methods are the operations, and an `InterfaceContract` (`orvex.contracts.interface`) that names the contract, gives it a `MAJOR.MINOR` version (`orvex.contracts.version`), groups the operations into capabilities, lists the error codes each may raise through the contract's error type, marks the operations that change state and the version each exists from. Only values cross: the annotated inputs and outputs are plain values, enums, generated contract models and frozen dataclasses of them (`orvex.contracts.serializable`); no live object, connection or callable. `UNSUPPORTED_OPERATION` can never be declared: a capability is provided in full or not at all. The interface contract of module `<m>` lives in `orvex.contracts.<m>.interface`, its kit in `orvex.contracts.<m>.kit` and its public test adapter, when it has one, in `orvex.contracts.<m>.adapter` (`orvex.contracts.registry`).
2. **The call envelope.** Every operation takes a `CallEnvelope` (`orvex.contracts.envelope`) as its first argument: `contract_name` and `contract_version` (the contract's version, never the module's or a physical format's), `correlation_id`, the effective `actor` or a verifiable reference to it, `project_id` and `revision`, and an `idempotency_key`, required on every operation that changes state. Every binding (`orvex.contracts.binding`) validates it before the implementation runs and fails closed with a typed `ContractCallRefused`: CONTRACT_ENVELOPE_INVALID for a missing, blank or mistyped field, a missing key or another contract's envelope; CONTRACT_VERSION_UNSUPPORTED for another major version or an operation that the provider's or the caller's version does not have. A caller at a newer minor version is served for the operations the provider has.
3. **Conformance kits.** Every interface contract ships a kit (`orvex.contracts.kit`): cases with a stable id, the operation they exercise, their expectation in words and the version they exist from, a recorded case count and no skip list. A kit leaves no operation without a case, and each operation that changes state has an idempotency case: the call is sent twice with one key and its effect must happen exactly once. The runner (`orvex.contracts.kit_run`, `kit_client`, `codec`) runs every case on a fresh implementation, once in process and once through the serializing binding, by a consumer at N-1 and at N, and adds the envelope cases the contract implies (each missing field and key, another contract, another major version), which must be refused before the implementation is reached. A provider at N-1 runs the kit of N: the cases of its version pass, the newer ones pass or are refused with CONTRACT_VERSION_UNSUPPORTED, never answered wrongly. An implementation that passes its contract's whole kit may replace the module.
4. **Consumers know contracts, not modules** (amends rule 3). `server` stays the only composition root, but only `server/assembly.py` names implementations, and only through each module's public `api` package. Every other consumer (`server`, the conformance runners, `tools/`, the repository tests) imports only `orvex.contracts`. `tools/checks/consumers.py` enforces it, in report mode until #486 step 7 makes it blocking and removes the `server` exemption.
5. **Module manifests** (amends rule 4). Each module ships `module.toml` (`orvex.contracts.manifest`): the interface contracts it provides (version, capabilities, the `api` attribute that implements each) and requires (version, capabilities), and the distributions its code and its tests import. Before the server starts, `assembly.py` refuses (exit status 3, `ASSEMBLY_REFUSED`) any combination in which a required contract has no implementation or more than one, a version that does not provide the required one, a missing capability, or an implementation lacking an operation of what it claims. Each module still owns its state alone (rule 4 unchanged); the manifest makes what it offers and needs explicit.
6. **Compatibility of behavior.** The record of every interface contract and its kit (`packages/contracts/interface-record.json`, `tools/contracts/interface_record.py`) is compared with the record at the last product release (`tools/contracts/interface_compat.py`): within a major version operations, signatures, capabilities, error codes and kit cases with their expectations may only be added, each addition existing only from a version after the release. A break needs a new major version (rule 6 of ADR-0004 applies to it). Rule 3 runs N against N-1 in both directions: each module's own tests run its kit by consumers at N-1 and N, and an implementation at N-1 runs the current kit with its own version as `provided`. The job that builds a module's last released implementation for that run arrives with the first released interface contract (#486 step 2); until then no released implementation exists.
7. **Standalone modules.** `tools/ci/standalone.py` builds a module's sdist and, from it, its wheel, installs it in a clean environment outside the repository with only `orvex-contracts` beside it, checks that its imports equal its declared dependencies, that its tests import no repository helper and that every contract it requires has a public test adapter (`orvex.contracts.adapter`, itself passing the contract's whole kit), and runs its own tests there, where a skipped test fails. A module thus starts and runs its own operations without the modules that only consume it.

## Alternatives considered
- **An envelope carried beside the call (context variables or a session object) instead of as the first argument:** less to write per operation, but invisible in the signature, impossible to serialize as a value and easy to lose across a process boundary.
- **Interface contracts as language-neutral documents with generated protocols:** symmetrical with the data contracts, but it adds a generator and a second description of each signature to keep in step; the record of rule 5 already gives a language-neutral view of each interface for comparison.
- **A second, complete implementation of every module** (#486 revision 3): proves substitution but duplicates about 41,000 lines; the kits, the assembly check and one real substitution (the semantic result cache, #486 step 5) prove it at a fraction of the cost.
- **Process isolation now:** belongs to the workers of #156; rule 1's value-only crossing, rule 2's envelope and the serializing binding make the contracts ready for it.

## Consequences
Every module gains a contract, a kit, a manifest and an `api` package, one module per step of #486, and its consumers move onto them; module error classes used across modules move into `orvex.contracts`. CI gains the interface record and compatibility check and the standalone job. The documents that say `server` knows the modules (`architecture/overview.md`, `AGENTS.md` §5, `engineering.md` §2 and §8, `modules/contracts.md`) are corrected when this ADR is accepted.
